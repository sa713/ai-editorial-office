## editorial decision frame

- Chosen route: strengthen the explicit bridge from the existing Customer
  Feedback Loop into the existing Editorial Learning Framework, add only the
  fields and owner-scoped guidance proven necessary by research, and validate
  the integrated behavior through the nine mission cases.
- Alternatives considered:
  - Create a new Feedback and Learning Intelligence framework.
    - Rejected: it would duplicate the two existing canonical owners.
  - Collapse all feedback and learning labels into one new taxonomy.
    - Rejected: feedback classification and knowledge disposition serve
      different decisions; replacing both would create migration and ownership
      risk.
  - Add automation, scoring, or mandatory retrospectives.
    - Rejected: the mission forbids evidence-free scoring, automatic promotion,
      and mandatory process weight.
- Writer/implementation contract:
  - Result type: canonical guidance patches, templates/journal alignment,
    representative-case validation, release documentation, and state sync.
  - Must include: source signal, evidence pointer, outcome, scope,
    classification, learning disposition, owner, proposed bounded action,
    review path, rejection/deferral, non-promotion, and Domain Pack use effect
    when material.
  - Must not include: new roles, pipelines, stages, gates, stores, taxonomies,
    automatic canon/backlog/roadmap changes, or Project Lead acceptance.
- Review focus: signal/noise boundaries; classification versus disposition;
  evidence and pattern thresholds; owner routing; non-promotion; Domain Pack
  use evidence; stale-learning correction/retirement; all nine cases; release
  state and memory alignment.
- Reroute triggers: synthesis cannot preserve both existing owners, any case
  requires automatic promotion, or implementation needs a forbidden system
  structure.

## evidence and review requirements

- Prefer primary or authoritative sources.
- Separate observations from inferred lessons and proposed actions.
- Require saved evidence and applicability scope before reusable promotion.
- Treat one anecdote as task-local, rejected, or deferred unless a reviewed
  high-impact exception is supported.
- Validate positive and negative outcomes, including Domain Pack value and
  unnecessary complexity.
- Keep Project Lead acceptance and canonical-owner action explicit.
- Independent Review Agent must inspect the complete diff and validation
  outputs; no second review gate is added.

## known risks

| Risk | Impact | Mitigation |
| --- | --- | --- |
| Duplicate feedback/learning taxonomy | Conflicting guidance | Preserve feedback classification and learning disposition as linked but distinct decisions |
| One-off feedback becomes policy | Governance drift | Default to task-local; require evidence, scope, owner, and review for promotion |
| Pattern count becomes evidence-free score | False certainty | Use qualitative sufficiency and high-impact exception with explicit evidence |
| Domain Pack telemetry becomes mandatory | Process bloat | Capture compact use/effect evidence only when a pack was actually activated and the effect is material |
| Every task gains a retrospective | Service weight | Trigger learning extraction only for material signals in existing artifacts |
| `/about` becomes canon | Memory drift | Sync only from repository owners and validate package |
