# Workflow speed review

## Где процесс тормозит

- Старт задачи часто требует много служебной подготовки до первого полезного результата.
- Оркестрация повторяет выбор пайплайна, риск, роли, артефакты и ограничения в нескольких местах.
- Handoff создаётся на каждый переход, даже если следующий шаг очевиден и уже записан в манифесте.
- Проверка иногда читает весь набор артефактов вместо объекта проверки, brief и evidence files.
- Финализация повторно валидирует то, что уже валидировал review.
- Задачи с несколькими версиями не всегда имеют короткий указатель, какая версия главная.

## Какие шаги можно объединить

- Для low-risk: `brief + compact manifest/status` можно вести одним коротким файлом, если статус и манифест не расходятся по смыслу.
- Для simple standard: `qa-checklist` можно встроить в `review.md`.
- `review-summary.md` можно не создавать, если `review.md` уже содержит verdict, blockers, next action.
- `finalization-checklist.md` можно встроить в `final_decision.md` для простых задач без смысловых изменений после проверки.
- Handoff можно пропускать, если роль не меняется и следующий шаг записан в манифесте.

## Где использовать compact path

- Короткие внутренние объявления без чувствительных фактов.
- Переписывание текста по данным пользователя, если новые факты не добавляются.
- Сравнение версий, где объект проверки ограничен.
- Авторская диагностика сырой идеи без готового решения.
- Подготовка структуры выступления или презентации, если нет публикационного риска.

Compact path не подходит:

- high-governance;
- продуктовые утверждения без контекста;
- внешняя публикация;
- юридические, HR, финансовые, медицинские, безопасностные, репутационные темы;
- спорные факты, цифры, даты, обещания, политики.

## Где review / revision избыточны

- Повторный review после микроправки, если проверяющий заранее задал узкий re-review scope.
- Полный review всех каналов после изменения одного абзаца в одном канале.
- Review-summary после review, где уже есть короткое решение.
- Полная финализация, если `final.md` равен утверждённому draft без смысловых изменений.

Нельзя убирать:

- первый независимый review перед финалом;
- повторную проверку после существенных изменений;
- проверку фактов и продуктовых утверждений;
- проверку границ diagnosis vs design.

## Где агенты делают лишнюю работу

- Chief Editor часто пересказывает пайплайн вместо выбора глубины и следующего шага.
- Writer иногда создаёт `outline.md` и `writer-notes.md` даже там, где черновик короткий и самодостаточный.
- Review Agent иногда выпускает несколько обзорных артефактов вместо одного плотного `review.md`.
- Final Editor может создавать notes/checklist без реальных изменений после review.

## Где слишком много чтения контекста

- Роли читают полный устав, роль, пайплайн, шаблон и KB даже для узкой правки.
- Задачи с длинной историей требуют чтения старых handoff-файлов, хотя нужен только последний.
- Ретроспективы часто полезны, но для текущей работы должны читаться выборочно.
- `project_tree.md` хорош для ревью системы, но не должен входить в обычный task path.

## Практическое правило скорости

Для каждой задачи перед стартом спрашивать:

1. Что является объектом работы?
2. Какая минимальная проверка нужна, чтобы не потерять качество?
3. Какие файлы нужны следующей роли?
4. Какие файлы можно не создавать, потому что их смысл уже есть в другом месте?
