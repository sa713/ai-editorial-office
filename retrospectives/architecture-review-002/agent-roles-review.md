# Agent roles review

## Где роли работают хорошо

- `chief_editor` хорошо держит рамку: выбор пайплайна, риск, следующий этап, финальное решение.
- `intake_agent` полезен для сырого запроса: цель, аудитория, формат, ограничения.
- `research_agent` защищает от письма из памяти модели.
- `writer_agent` отделён от проверки и финализации.
- `ux_writer` отдельно держит продуктовый контекст и не должен придумывать поведение продукта.
- `review_agent` сохраняет независимость и проверяемость.
- `final_editor` ограничивает пост-review изменения.

## Где агенты пересекаются

- `chief_editor` и `intake_agent`: оба могут уточнять задачу, риск, пайплайн, ожидания.
- `chief_editor` и `review_agent`: оба проверяют готовность и артефакты.
- `writer_agent` и `final_editor`: оба могут править текст, но финальный редактор должен быть ограничен approved review.
- `research_agent` и `review_agent`: оба смотрят источники, но research собирает evidence, review проверяет использование.
- `ux_writer` и `research_agent`: оба работают с продуктовым контекстом, но UX writer не должен расследовать продуктовую истину вместо источников.

## Лишняя передача между ролями

- Intake -> Chief Editor -> Research -> Chief Editor -> Writer может быть тяжёлым для source-light задач.
- Review -> Final Editor -> Chief Editor иногда нужен, но для low-risk может быть укорочен через compact final decision.
- Changes requested -> Writer -> Review не должен превращаться в полный цикл, если review задал узкий re-review scope.

## Где уменьшить handoff

- Если переход стандартный и все файлы указаны в манифесте, handoff должен быть только delta.
- Если роль не меняется, handoff не нужен.
- Если задача закрывается для пользователя, использовать `compact-handoff.md`, а не role handoff.
- Если review approved без blockers, handoff к finalization может быть одной строкой внутри `review.md`.

## Где specs слишком подробные

- Все agent specs повторяют глобальные запреты: не нарушать устав, не обходить review, не создавать лишние файлы, не придумывать факты.
- Многие роли включают sequencing, который уже принадлежит пайплайнам.
- Role specs содержат длинные структуры выходных файлов, которые лучше держать в шаблонах.
- Context loading rules в ролях похожи друг на друга и могут жить в одном общем профиле.

## Что менять

- Сократить role specs до поведения роли, границ решений, входов, выходов и stop conditions.
- Убрать из ролей повтор полного lifecycle.
- Оставить в ролях только role-specific risks.
- Добавить короткую таблицу "who owns what" вместо повторения в каждом файле.

## Что не менять

- Не добавлять новых агентов.
- Не возвращать отдельного Editor Agent.
- Не делать review optional.
- Не сливать research и writing при фактических утверждениях.
- Не позволять final_editor переписывать смысл после review.
